## 一、定位与边界（先定调，再谈功能）

**一句话定位**：QQ-Live-Digest 是一个 **AI 驱动的 QQ 群实时信息处理与通知聚合系统**——把高噪声群消息转换成
通知、待办、截止时间等**可执行信息**，而不是把聊天记录原样转发。

**核心链路**（只读）：

```
QQ → NTQQ/NapCat → OneBot v11 → 本地规则/去重/打分 → 可选 LLM(千问)
   → 结构化存储(SQLite) → 推送(WxPusher 等) / PWA 待办台 → MCP/Agent 接口（查询 + 确认后写待办）
```

Tailscale / SSH 隧道属于**访问层**，不参与消息理解；NapCat 掉线只影响接收，不影响数据本身。

**三条红线（长期不变）**：

1. 不让 AI/Agent 自由操作 QQ（发送、踢人、改群设置一律不做）。
2. 主动发送 QQ 消息属于独立高风险分支，不与只读摘要能力混在一起。
3. 不在单用户体验成熟前做多用户 SaaS。

**决策原则**：先验证，再采纳。评论区提出的是**候选方案**，不是需求单；任何功能都要先回答
"它解决的是成本、隐私、部署、漏报、误报、可解释性、可替换性中的哪一个真实问题"。

## 三、优先级评分模型

对每个候选按 6 个维度打 1–5 分，加权求总分（满分 5.0）：

| 维度 | 权重 | 1 分含义 | 5 分含义 |
| --- | --- | --- | --- |
| 用户价值 V | 30% | 锦上添花 | 直接解决高频痛点 |
| 战略契合 S | 20% | 偏离主线 | 强化定位/护城河 |
| 成本可控 C | 15% | 工期长、改动大 | 低成本、可快速交付 |
| 风险与安全收益 R | 15% | 引入新风险 | 显著降低风险 |
| 社区/开源收益 M | 10% | 无外溢价值 | 明显提升可贡献性与曝光 |
| 独立可交付 I | 10% | 强依赖前置 | 可独立落地 |

**总分 = 0.30V + 0.20S + 0.15C + 0.15R + 0.10M + 0.10I**，按分数与阶段综合定优先级。

## 五、阶段目标与验收标准

**Phase 0（0–3 周）目标：让别人看得懂、装得起来、敢贡献。**
验收：仓库有 Issue/PR/CONTRIBUTING 模板与 FAQ；`doctor` 能一键诊断全链路；安全测试进入 CI；
有一条 30 秒脱敏 Demo；决策日志可解释"这条为什么推/不推"。

**Phase 1（1–2 个月）目标：AI 可控、可测、可替换。**
验收：切换模型只改配置；能看日/周/月 token 与成本；每条候选有 confidence 与依据；
低置信度走人工确认且反馈可回收；每群可独立配策略；有第一版 Benchmark 基线数字。

**Phase 2（2–4 个月）目标：从消息处理升级为个人信息中枢。**
验收：跨群同一事件聚合为一条；明确时间可导出 ICS 并识别时间冲突；
提供只读 REST + MCP（只读 5 Tool），并在 `confirm` 约束下开放待办写入（仅 `tasks`、逐次审计）；
Cursor/Claude 能安全查询通知、待办、截止时间。

**Phase 3（4–6 个月+）目标：生态扩张。**
验收：Linux/Docker 可跑通；英文文档 + 架构图齐备；本地模型可作可选 Provider 并通过 Benchmark 门槛；
规则 DSL 可预览后启用。

## 六、明确暂缓 / 不做

| 事项 | 判断 |
| --- | --- |
| 把整个项目改成 Agent，让 Agent 接管消息处理 | 暂缓 — 固定流水线已够用，Agent 只作上层可选能力 |
| 让 Agent 自由操作 QQ（发消息/踢人/改群设置） | 不做 — 账号与权限风险不可控 |
| 一开始就做大量 MCP Tool | 暂缓 — 首版 4 个只读 Tool 足够验证价值 |
| 为了 Star 强行堆功能 | 不做 — 先提升 Demo/README/部署/测试/贡献体验 |
| 把 Qwen 写死在业务层 | 不做 — 应尽早做 Provider 抽象 |
| 直接做多用户 SaaS | 长期 — 单用户体验还有大量空间 |
| 常驻大模型 + 多个窄模型换省 token | 谨慎 — 先用 Benchmark 验证，避免硬件成本反噬 |
| 研究"免踢/绕风控"方案 | 不做 — 只做限频/触发/权限隔离等风险降低 |

## 八、我的主观判断（一句话结论）

- **最该做的**：不是继续堆"看起来很 AI"的功能，而是把系统变得**可解释、可测、可替换、易部署、易贡献**。
- **最该长期保留的路线**：本地规则降噪 → 可选轻量模型 → 高能力模型 → 结构化数据 → 推送/PWA → MCP/Agent 作为上层接口。
- **最该警惕的路线**：为了省一点 API 费，过早引入多模型常驻、复杂 Agent 编排或主动控制 QQ——
  那会把项目从"真正解决问题的工具"变成"技术栈展示项目"。
- **评论区最大的价值**：不是某个具体技术名词，而是它暴露的真实需求——
  成本、隐私、部署门槛、漏报、误报、可解释性、模型可替换性、AI 接入、社区协作、可靠性。
