> 新的高频问题先进入本文，再决定是否做成功能。最后更新：2026-10-08

## 一、定位与概念

### Q：这个项目到底是什么？有什么用？

AI 驱动的 **QQ 群实时信息处理与通知聚合系统**。它解决的是“群消息太多、重要通知容易被刷过去”的问题：
把高噪声的群消息转换成**通知、待办、截止时间**等可执行信息，而不是把聊天记录原样转发。

### Q：我的群消息很少，是不是就没什么用？

**是的。** 项目价值与消息噪声正相关：群越多、通知越分散、一天消息越多，收益越明显。
我们不会把它包装成"所有人都必须用"。

### Q：这是不是一个 QQ 机器人（QQ Bot）？

不宜简单称为 QQ Bot。更准确的说法是 **QQ 群信息处理 / 通知聚合系统**。
NapCat / OneBot 只负责接入，核心价值在后处理（过滤、去重、摘要、待办、推送）。

### Q：原理是 Agent 吗？

**不是。** 当前是**固定流水线**：程序控制接收、过滤、存储、去重、推送，LLM 只负责其中一部分语义理解。
Agent 属于未来的**上层可选能力**，不会反过来接管底层消息处理。

### Q：这和 NapCat / OneBot / NTQQ 是什么关系？中间件为什么这么多？

- **NTQQ / QQNT**：新版 QQ 客户端本体。
- **NapCat**：在 NTQQ 之上把 QQ 消息接出来的框架。
- **OneBot v11**：统一的机器人事件 / 接口协议层。
- **QQ-Live-Digest**：负责后面的筛选、摘要、任务提取、去重和推送。

层次多不代表重复造轮子，真正需要控制的是**依赖复杂度**。

### Q：这算 MCP 吗？

**目前不是。** 未来可以增加一个**只读 MCP Server**，让 Cursor / Claude 等 AI 安全地查询通知、待办、截止时间和历史消息，
但不会让 AI 直接控制 QQ。见 `docs/ROADMAP.md` 的 A1 / A3。

## 二、AI 与模型

### Q：为什么用千问（Qwen）？

主要考虑中文通知理解、视觉（图片）能力、成本和长期可用性。**不要把 Qwen 宣传成"一定最强"**——
模型可替换是项目的明确方向（Provider 抽象，见 ROADMAP A4）。

### Q：一定要 AI 才能运行吗？

**不必。** 本地规则可以完成基础过滤与摘要；LLM 属于**增强层**，调用失败时自动回退本地规则，不影响推送。

### Q：为什么不把所有消息直接丢给 AI？

因为会浪费 token、增加延迟和噪声，还会放大模型误判。正确思路是**本地预筛 → 只把候选交给模型**。

### Q：能不能换别的模型？

应该能，也会做。长期方向是 Provider / Adapter 抽象，业务层不直接绑定某一家 SDK。
当前代码默认走阿里云百炼（OpenAI 兼容接口），改 endpoint + key + model 即可对接兼容实现。

### Q：能不能接 Cursor / Claude 等 Agent？

适合通过 **MCP 暴露只读查询能力**（“总结今天的重要通知”这类），而不是让 Agent 直接操作 QQ。

## 三、降噪与可靠性

### Q：重复消息和闲聊怎么过滤？

本地规则先筛：文本归一化 → 精确 / 相似度去重 → 只对候选调用模型；
最近已推送内容还会按时间窗口（默认 6 小时）做二次去重；同一条通知被多个群转发会合并为一条并标注“跨群重复”。

### Q：会不会漏掉重要通知？

**任何分类系统都无法保证零漏报。** 我们靠补采、重试、规则回退、原文依据和人工纠错来降低风险；
高风险候选不会被轻易丢弃。如果你的场景对漏报极度敏感，请保留原文回看入口并在待办台做纠错。

### Q：群文件、截图能识别吗？

可以。PDF / Word / Excel / PPT / zip 和图片（OCR）都能解析并纳入摘要。
但必须有**大小、页数、频率、格式和安全限制**（如压缩炸弹防护），完整支持范围以 README 为准。

## 四、安全与风控

### Q：只读和主动发消息有什么区别？

当前是**只读**路线：只接收群消息，代码不调用 QQ 发送接口。主动发送会把账号风险从“读取”扩大到“写入 / 机器人行为”，
属于**独立的高风险分支**，不与只读摘要能力混在一起。

### Q：主动问答 Bot 能不能降低被踢风险？

可以做限频、@ 触发、冷却、短回复、独立小号等**风险控制**，但**只能降低风险，不能保证不被踢**。
我们不做“伪装成人类 / 绕过平台检测”式设计。

### Q：研究所谓“免踢 / 绕风控”方案可以吗？

**不建议。** 平台规则不可控，正确做法是限频、触发条件、权限隔离等风险降低，而不是规避检测。
注意区分 **QQ 层风险**（账号行为）与 **SSH / RDP / Tailscale 网络层风险**，两者不是一回事。

## 五、部署与网络

### Q：Tailscale 是必须的吗？它和 QQ 消息有什么关系？

不是必须。Tailscale（或 SSH 反向隧道 / 同局域网直连）解决的都是**远程安全访问 PWA** 的问题，属于**访问层**；
它和 QQ 消息理解是两层，Tailscale 挂掉只影响远程访问，不改变核心消息处理。

### Q：需要电脑一直开着吗？

实时接收需要 NapCat 与服务在线。关机期间只能依赖历史补采 / 恢复后的补偿机制（默认回溯 24 小时，
由 `QQ_DIGEST_CATCHUP_HOURS` 控制）。

### Q：关键词和内容能不能自定义？

可以扩展为配置化规则（当前已有环境变量与群级策略雏形）。
更合理的方向是**群级策略 / 规则 DSL**（见 ROADMAP A9 / A10），但不要声称所有规则现在都已做成配置项。

## 六、协作

### Q：别人说“用 GPT 改了代码，希望 Pull 一下”是什么意思？

通常是对方 Fork 或建分支改完代码后提交 **Pull Request（PR）**，希望上游审查并合并。
我们会按 `CONTRIBUTING.md` 和 PR 模板审查：**不会因为用了 GPT 就直接合并，也不会直接拒绝**。
